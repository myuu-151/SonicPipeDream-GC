# Session log: 29-30 September 2026

A log of one long working session with Claude Code (Claude Opus) on the GameCube builds: Castle
Crashers GC, then Sonic Pipe Dream GC. Most of it went into one bug: a marathon's change of
zone turning the whole 3D picture into "stripes to a single point". It is written up in full,
dead ends included, because the dead ends are the lesson. The rules that came out of it are in
the engine's [GameCube dos and don'ts](https://github.com/myuu-151/Octave-libogc/blob/main/Documentation/AI/GameCubeDosAndDonts.md).

## Stage 4's loading hang

**Seen:** on hardware, loading stage 4 ("emerald 4") hung on the loading screen.

**Cause:** the heap. A drop or rise piece needs one 156 KB block for its vertex array, and by the
fourth stage of a session the heap had no piece that big left.

**Fix** (engine `BigBlockCache_Dolphin.cpp`, `System_Lua.cpp`, `AssetManager.cpp`; this repo's
`Screens.lua`):
- `System.PinBlocks(bytes, count, reserve)` reserves the pieces' array blocks at boot, while the
  heap is still whole, and keeps them for good. `PIECE_ARRAY_BYTES` lists the four sizes.
- The cache gives back the smallest block that will do, not the biggest, when an allocation fails.
- A load that runs out of memory fails that one load (logged) instead of taking the game down.
- 143 stage loads in a row in a fast test, with no failures.

## The marathon's stripes

### How it showed

In a marathon or time attack, at a change of zone, the stage "collapsed": every polygon became
a long stripe running to a single point, the frame rate fell through the floor, and the game
eventually went down. It was reported on hardware first, then reproduced in Dolphin. The 2D HUD
stayed perfect throughout.

### What it was

libogc's `guMtxConcat`, the routine the renderer uses to make every object's model-view
matrix, is broken in libogc 3.0.4.

- On the GameCube `guMtxConcat` is `ps_guMtxConcat`, written in paired-single assembly. It needs
  the implied bottom row of an affine matrix, `{0, 0, 0, 1}`. It takes the `{0, 1}` from a
  constant, `Unit01`, with `psq_l f31, Unit01@sdarel(r13)`.
- `psq_l` has only **12 bits** of offset. The relocation, `R_PPC_SDAREL16`, writes **16**. The
  top four bits land in the instruction's W and I fields, so in the linked game the instruction
  is `psq_l f31, 608(r13), 1, 0`.
- W=1 means "load one float and make the other 1.0", and 608 bytes past r13 is not `Unit01`. So
  the routine's "0" is whatever float the link puts at r13 + 608. Its "1" is always right.
- Every model-view matrix then gets that float times the camera's translation in its third
  column. While the float is 0, all is well.
- In this game, r13 + 608 fell inside `sPiece`, the 32 KB static buffer that
  `StaticMesh::StageColorsFrom` reads vertex data into. That buffer is first filled during a
  marathon's hold, when the next zone's colours are read in.
- From that frame on, every 3D object in the game was drawn with a garbage matrix, for as long
  as the game ran: the pipe, the sky dome, Sonic, the rings. The HUD doesn't go through that
  routine, which is why it stayed perfect.

**The fix:** the engine now calls `c_guMtxConcat` at all eight places, libogc's plain C version
of the same multiply. `GxUtils.h` also points the name `guMtxConcat` at it, so a new call
written the usual way can't bring the broken one back. The reasoning is in a comment there.
- It is the only such instruction in libogc: every other paired-single routine reaches its
  constants with `lfs`, which has the full 16 bits.
- Nothing else in the game calls `ps_guMtxConcat`. The fixed build's `.elf` has 0 calls to it
  and 8 to `c_guMtxConcat`.
- Verified in Dolphin with the harshest test available: a colour change every 3 seconds all
  through a marathon (`GcTest.hold = 3`), with 256 KB of memory taken away. Before the fix it
  broke within seconds of the first change.

### Why it took so long

The bug depends only on **where the linker puts things**, and on what gets written there. That
made it look like memory corruption, and every change to the code moved the memory, so every
change seemed to affect it. Three earlier "fixes" were really this, misread:

- **"An unaligned static buffer flashed garbage over the 3D view"** (the reason `sPiece` is
  aligned). Aligning it moved the buffer, so r13 + 608 landed somewhere else.
- **"A block allocated mid-game made the picture flash with garbage while it was held"** (the
  reason the recolour's staging buffers are allocated behind the loading screen). The same
  effect, through a different layout.
- **"The emerald's display lists, built in the middle of a frame, turned every polygon into
  stripes"** (the reason each marathon preloads all seven emeralds). The same bug again. Display
  lists built during a frame were shown to be harmless: libogc flushes the write-gather pipe
  before it switches FIFOs.

All three changes stay, for their real merits: the buffer is aligned for the SD card's DMA, and
nothing big is loaded or allocated mid-run. Their comments now say so.

### The trail

In order, and what each step showed:

1. **Bisecting the hold** (Lua flags): with the recolour off, fine through zone 4; with only the
   colour reading and nothing applied, broken. So reading the colours off the disc was enough.
2. **Checks on everything the reading might touch**, each finding nothing wrong: node vtables,
   display list checksums, vertex position checksums, the camera, the zone's join data. A heap
   tripwire watched every block the GPU reads (FIFO, display lists, vertex arrays, textures) for a
   free or a new allocation over it.
3. **Two read-only code audits**, by sub-agents:
   - The FIFO and display list handling in libogc is sound, so no GPU command stream corruption.
   - It found a real heap race: with `Logging=1`, the loader thread rebuilt the on-screen log's
     widgets under the main thread. It was fixed, but it was not this bug, which came back with
     it fixed.
4. **Dolphin's GPU logs** (`CP`, `GP`, `PI`, `PE`, `Video`): no "unknown opcode", so the GPU was
   being fed well-formed commands carrying wrong data. *This should have been step one.*
5. **A check on every model-view matrix sent to the GPU.** Every object's third column was
   garbage, and the garbage was the same for all of them: exactly the camera's translation times
   one number. That pointed straight at a `{0, 1}` constant inside the multiply.
6. **A canary**: a known multiply checked at points through the frame. It failed first "during a
   disc read", which looked like a disc DMA overwriting the constant.
7. **A gdb watchpoint on the constant**, through Dolphin's GDB stub. It never fired, even with
   Dolphin's debug mode on. A breakpoint had silently done nothing without debug mode.
8. **Dumping the constant from the game**, next to the last 16 disc reads and DMAs. It was
   intact. The reads were fine too, and one of them was the colour read into `sPiece`.
9. **Disassembling `ps_guMtxConcat`** showed `psq_l f31, 608(r13), 1, 0`, and r13 + 608 is inside
   `sPiece`. The `.o` in `libogc.a` shows the `R_PPC_SDAREL16` relocation on a `psq_l`.

### Also fixed on the way

- **The on-screen log** (engine `Log.cpp`, `Renderer.cpp`). Lines are queued and written into the
  console widget on the main thread (`FlushConsoleMessages`). Only builds with `Logging=1` were
  affected.
- **`GxWaitGpu` dropped a frame** (engine `Graphics_GX.cpp`). It marked the frame in flight as
  done, so that frame was never shown, and the next was copied into the framebuffer on screen
  (torn). It happened on every frame of a hold and of a sky's change of stars.
- **The vertex cache** (engine `Graphics_GX.cpp`). `GX_InvVtxCache()` now runs when a compact
  vertex array is made. The big block cache hands blocks on, and the GPU's vertex cache is keyed
  by address. Only the console has that cache; Dolphin doesn't emulate it.

## Zone changes on the console

With the stripes gone, the zone changes themselves went wrong on hardware, one thing after another.

### "It just lagged heavily and then never switched the zone"

**Cause:** the hold read about 5.4 MB off the SD card on the main thread, a piece a frame:
- the new palette's pipe meshes, for their colours (about 2 MB);
- the new sky's eight star frames (4 MB).

The card gives 0.3 to 0.7 MB/s, so the game ran at 7 fps for half a minute.

**Fix:**
- **The pipe's colours come from memory.** `native/make_pipe_palettes.py` writes
  `PipePalettes.lua`. Across the ten piece meshes, a vertex's seven palette colours come in only
  1,497 combinations. So the file holds a table of those combinations and a 2-byte index per
  vertex: 133 KB for every palette of the whole pipe. `StaticMesh:SetPaletteColors` recolours
  the meshes in place.
- **The sky's stars are read in the background.** `Texture:ReloadFromAsync` runs on
  `SYS_ReadFileRangeInBackground`, a thread below the asset loader.

### "The skybox freezes"

**Cause:** the background reader took the whole card, and the sky's streamed diamond frames
stopped coming.

**Fix:** after each 32 KB piece, the reader rests as long as the piece took, so the card is
shared about half and half.

### "The skybox took a while to catch up"

**Cause:** the pipe changed at a fixed time into the hold. The sky changed only once its stars
were in, seconds later on a slow card.

**Fix:** the pipe and the sky now change together, once the stars are in (`TickFade`). Two
safeguards:
- A second change of sky waits for the first to finish.
- A change whose stars never arrived leaves the sky alone. Reloading all eight frames at once in
  the middle of a run needs 4 MB.

### "Everything freezes"

This one took three test runs to pin down.

**Seen in Dolphin:**
- "Lua Error: not enough memory", every 1.7 s, from the second or third zone change on.
- The first guess was the old sky's diamond frames not being freed. That was a real leak, now
  fixed, but it wasn't the cause.
- The period gave it away: 1.7 s is how long one zone takes to build.

**Cause:** the run's centre line, one small table per frame, was kept in one Lua table for the
whole run. Past 8192 frames, Lua wanted that table's slots in one 128 KB block. The heap had
megabytes free but no piece that big. So each time the next zone was built:
1. Joining it to the run failed.
2. It was built again.
3. It failed again.

Meanwhile the run went on to the end of its track.

**Fix:**
- `TrimBehind` takes the passed frames out and moves the rest down, so the table never holds
  more than about two zones. `data.pathBase` is its first frame.
- It drops the passed pieces' places too.

**Seen next:** with that fixed, the run got further, then ran out in the engine instead:
- a diamond frame found no 65,600-byte block;
- then an asset read found no 32 KB window;
- then the game stopped.

Two things were wrong:
- **The sky frames' reserved blocks never fit.** Their pin reserved 65,536 bytes, and a frame's
  block is 65,600 with its header.
- **Lua's heap ran a megabyte behind.** With the collector at a stepmul of 400, Lua's heap rose
  from 2.8 to 4 MB each time a zone was built.

**Fix:**
- Eight frame blocks are reserved at boot at the true size.
- Two 32 KB read windows are reserved too.
- The collector runs at a stepmul of 1000. Lua now peaks at about 3.3 MB, and the heap keeps
  1.8 to 2.6 MB free.

**Verified:** 7 minutes in Dolphin with every background read slowed to a console card's pace:
- two marathons back to back, five zone changes in all;
- no failed allocation, load or script;
- the pipe and the sky changed together every time.

**Also:**
- **Clearer out-of-memory errors.** The engine now logs a failed Lua allocation
  (`LUA ALLOC FAILED`: the size, the free heap, the Lua lines that asked) and a failed
  `operator new` (`C++ ALLOC FAILED`, with addresses for addr2line). Lua's own message names no
  line.
- **Reliable disc reads.** The disc reader's bounce buffer is static: under memory pressure its
  `memalign` failed, and reads failed part way.

### The evening: hardware tests

Several hardware round trips, in order:

- **"It doesn't even switch zone on the emerald":** the pipe was waiting for the sky's 4 MB of
  stars before changing. Now the pipe changes on the emerald whatever the sky is doing (`TickFade`).
- **The sky changes with the pipe, from ARAM.** While a zone is played, the next zone's star frames
  are read in the background into ARAM (`Texture:StashFrom`, 4 MB of the console's 16 MB audio RAM).
  At the emerald each frame comes in by DMA in a few milliseconds (`ReloadFromStash`). The main
  thread never reads the card for it: the reader thread parses each file's header itself
  (`Texture::LocateTexels`). A 6-second freeze after the switch was the sky then refilling all
  eight frames from the card; `Sky.starsSky` remembers which sky the stars already hold.
- **The sky stuttering in every stage was the SD log.** Each write to `octiso.log` holds the disc
  lock for 50 to 130 ms. With the log header removed, the sky animated properly.
- **One ISO handle per reading thread** (`System_Dolphin.cpp`). With a single shared `FILE`, every
  change of reader was a seek and a lost read-ahead buffer. This fixed the time attack's sky stutter.
- **A zone is joined a slice a frame** (`AppendZone` in the generator's coroutine). In one go it was
  a third of a second in one frame.

**Still open:** Sonic is pulled back a little when control comes back after an emerald. It's in
Dolphin too, with every frame 16.7 ms, so it's a position jump, not a hitch. Putting the old track
trimming back didn't change it. The next test is the last committed scripts, in Dolphin, with
`GcTest.zoneSections = 1` (a zone change every ~20 s).

## What to do differently

- **When all the 3D is wrong and the 2D is fine, check the matrices first.** One per-draw check
  found in one run what hours of memory checks did not.
- **Turn on Dolphin's GPU logs at the start** of any graphics bug. They tell a bad command
  stream from bad data.
- **"Memory corruption" that moves with every code change can be a bad address in the reader.**
  Dump the memory before hunting a writer, and disassemble the code that reads it.
- **A fix that works but can't be explained isn't a fix.** Three layout-shuffling "fixes" hid
  this bug and let it come back.
- **An error that repeats at a steady beat is something retrying.** Match the period to what the
  game repeats. 1.7 s was one zone's build, and that led straight to the join.
- **Slow Dolphin's reads to a console card's pace** before calling a streaming change done. At
  Dolphin's speed, the sky's reads finished in time and none of this showed.
- **Dolphin's GDB stub needs debug mode** for breakpoints and watchpoints:
  `-C Dolphin.General.GDBPort=2345 -C Dolphin.Interface.DebugModeEnabled=True`.

## Test tools made

These live in the session's scratch directory; recreate them as needed.

- **`spd_build.ps1`**: builds the engine (2 jobs, below-normal priority), then packages the ISO
  (idle priority) with the root `Octave.exe -headless -project ... -build GameCube`.
- **`spd_run.ps1`**: runs the ISO in a scratch Dolphin with:
  - its own user folder, muted;
  - `FastDiscSpeed`, and `EmulationSpeed=0` (unlimited);
  - screenshots every N seconds, and the log copied at the end.
- **`GcTest.lua` switches**: `marathon`, `autoplay`, `wait`, `free`, and `hold = 3` for a colour
  change every 3 seconds. All of them off (`GcTest = {}`) in anything committed.
